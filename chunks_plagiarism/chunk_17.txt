The interpretation of feature importance scores in financial contexts requires some care. A feature can be highly important not because it carries unique predictive information but because it is correlated with the underlying signal in ways that the model finds easier to exploit than the signal itself. In our case, the dominance of the one-lag close is consistent with both interpretations: it could indicate that the model is essentially predicting the next return as a small perturbation of the most recent return (a momentum-like behaviour), or it could indicate that the close-price feature is the most efficient encoding of state that the model has access to. The training dynamics, the regime-conditional performance discussed in Section 5, and the comparison with classical baselines together support the latter interpretation.

4.13 Database Schema and Persistence

The persistence layer uses a small relational schema implemented in SQLite. The schema centres on five tables. The first, sessions, records the metadata of each trading session including its start time, end time, configuration snapshot, and final outcome. The second, trades, records every executed trade with foreign-key reference to its parent session, the entry and exit prices, the entry and exit timestamps, and the realised profit and loss. The third, signals, records every signal produced by the forecaster — even those that did not result in trades — together with the model's confidence score and the strategy engine's reason for action or inaction. The fourth, parameters, records every change to the user's risk parameters or strategy configuration, supporting a complete audit trail. The fifth, alerts, records every notification sent through the messaging interface and the corresponding acknowledgement, if any.

The schema is intentionally minimalist. We considered and rejected a more elaborate schema that would have decomposed each table into multiple normalised tables. The rejection was based on the observation that normalisation increases query complexity without providing material benefit for an application whose largest table — signals — accumulates only on the order of a few thousand rows per day. A flat schema is faster to query, easier to back up, and simpler to inspect manually, which are all advantages for a single-operator system.

4.14 Security Architecture

The security architecture has three layers. At the storage layer, all sensitive data — exchange API keys, account credentials, and the operator's Telegram bot token — is encrypted at rest using AES-256 in CBC mode with a key derived from a user-supplied passphrase via PBKDF2. The agent does not retain the passphrase in memory beyond the duration of a single session and prompts the user to re-enter it at startup. At the network layer, all communication with external services uses TLS, and the agent verifies certificate chains against the operating system's trust store. Plaintext HTTP is not supported. At the access-control layer, the messaging interface verifies the identity of incoming commands against a configurable allowlist of Telegram user IDs, and any command from an unrecognised sender is logged but ignored.

An important consequence of the storage encryption is that the agent cannot autonomously recover from the loss of the user's passphrase. This is a deliberate trade-off: a recoverable storage scheme would necessarily contain a back door that an attacker could exploit, so the security model treats passphrase loss as equivalent to permanent loss of access to the encrypted credentials. Users are warned about this trade-off during initial setup and are encouraged to store their passphrase in a password manager that the agent does not have access to. The conservative posture matches the recommendations in the broader security literature and aligns with the principle that any single-purpose credential should not be entangled with the application that uses it.

A separate concern is the authentication of the agent itself to the exchange. The Binance API supports two authentication mechanisms, a long-lived API key with HMAC-SHA256 message signing, and a shorter-lived JWT bearer token. We use the HMAC-SHA256 mechanism because its support across the major exchanges is broader and because the rotation of long-lived keys is easier to operationalise in a single-operator setting than the rotation of bearer tokens. The agent monitors API responses for indications that the key may have been compromised — for example, an unexpected withdrawal request — and includes a kill-switch that immediately invalidates the in-memory key and halts trading on any such indication.

4.15 Development Process and Tooling

The system was built in two-week iterations using an Agile process. Each iteration began with a brief survey of pilot traders and ended with a working increment that could be exercised on a paper-trading account. Requirements were prioritised using the MoSCoW scheme: real-time order routing, LSTM prediction, and instant-messaging alerts were "must-have"; custom strategies and the performance dashboard were "should-have"; multi-exchange support was "could-have"; and social-trading features were explicitly deferred to "won't-have" for the scope of this project. The production implementation is in Python 3.10 and relies on TensorFlow for the LSTM, Scikit-learn for classical baselines and feature scaling, TA-Lib for technical indicators, Pandas and NumPy for data manipulation, and SQLite and Redis for persistence.
