The objective is to choose a policy pi mapping states to actions that maximises the expected risk-adjusted return over a long-run horizon. We use the annualised Sharpe ratio as the principal scalar objective, with the maximum drawdown over the evaluation window serving as a hard constraint. Formally, the policy pi-star is defined as the argument maximum, over the space of feasible policies, of the expected Sharpe ratio of the realised return path subject to the constraint that the maximum drawdown does not exceed a configurable threshold.

This formal statement makes explicit the two-stage structure of the optimisation problem. The expected Sharpe ratio is the quantity we want to maximise; the drawdown constraint is the quantity we want to bound. Equivalently, we are looking for the policy that produces the highest risk-adjusted return among the policies that survive the worst-case drawdown bound. The risk-management framework discussed in Section 4 is essentially the operational expression of the drawdown constraint, while the LSTM forecaster and strategy engine together produce candidate policies that maximise the Sharpe-ratio objective subject to the constraint.

3.3 User Personas

Three user personas guided the design of the agent's user interface and feature set. The first is the early-career retail trader, typically aged twenty to thirty, with a few hundred to a few thousand dollars of trading capital and a full-time obligation outside of trading. This persona is technically literate but not a software developer; they can install a Python package and edit a configuration file but cannot debug a stack trace. They want the agent to run reliably without supervision and to surface notifications through a channel they already check, which in practice is a messaging app on their phone.

The second persona is the technically sophisticated retail trader, typically aged thirty to fifty, with a few thousand to a few tens of thousands of dollars of trading capital and either a software-engineering background or a formal quantitative-finance education. This persona wants the same reliability as the first but also wants the ability to extend the agent — to add a new strategy, to integrate a new data source, to plug in a custom risk model. The internal extensibility of the agent — the explicit message-bus boundaries, the well-documented persistence schema, the modular strategy interface — is designed to accommodate this persona.

The third persona is the small-firm proprietary trader, typically a part-owner of a regional brokerage or a small fund, with tens of thousands to a few hundred thousand dollars of trading capital and a strong preference for transparent, auditable trading logic. This persona is unlikely to use the agent as a primary execution venue but may use it as a back-office tool for evaluating ideas, for backtesting strategies, or for exposing controlled trading capability to junior analysts. The data-export and audit-trail features of the agent are designed with this persona in mind.

3.4 Cost Model

The economic feasibility of any retail trading agent depends on the relationship between the agent's expected per-trade gross return and the round-trip transaction cost. We model the round-trip cost as the sum of three components: the explicit exchange fee, the realised slippage against the decision price, and the funding cost (for perpetual futures positions held across funding intervals). On the Binance USDT-margined futures venue we use in our primary deployment, the explicit fee for a small market order is approximately two basis points each way, the realised slippage on retail order sizes is empirically a few basis points, and the funding cost is approximately one basis point per eight hours for typical positions. The total round-trip cost on a typical retail order is therefore approximately five to seven basis points.

This cost model has direct implications for the design of the agent. The strategy engine's confidence threshold and magnitude threshold are set so that the expected value of a trade — the product of the directional accuracy advantage and the expected magnitude of the next move — comfortably exceeds the round-trip cost. A trade whose expected value is below cost is suppressed by the strategy engine even if the directional signal is high-confidence, because executing such a trade is a money-losing proposition in expectation. The threshold parameters are exposed to the user and can be adjusted to reflect the user's specific cost structure.

3.5 What an Agent Must Solve

A software agent that replaces the human in this loop has to do substantially more than issue a forecast. It must, at minimum, solve five interlocking problems. We address each in turn because each shaped the architecture in concrete ways.

First, the agent must maintain a live data pipeline robust to API disconnections, rate limits, and malformed payloads. A naive implementation that polls a REST endpoint every few seconds and prints the last price is a demonstration, not a system; real agents must gracefully handle WebSocket disconnections, exchange-imposed throttling, and the routine chaos of malformed or out-of-order messages that characterises public data feeds. The cost of getting this wrong is not merely an occasional missed update; it is a silently corrupted view of the market that causes the agent to make decisions based on stale or inconsistent state. The mitigations are well known but not always implemented: persistent WebSocket connections with exponential-backoff reconnection, REST polling as a fallback, NTP-synchronised local timestamps, idempotent message handling, and explicit validation of every payload against a schema.
